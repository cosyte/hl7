# @cosyte/hl7 0.1.0 release readiness

- package: `@cosyte/hl7`
- from: `0.0.10`
- target: `0.1.0`

This file is the evidence a maintainer says yes or no to `0.1.0` on. It is validated by
`scripts/release-readiness.ts`, which reads it beside `.changeset/`, `package.json` and
`release/public-api.json` and refuses if any of them describes a different release from the one this
file claims. It is not in `package.json#files`, so no consumer receives it.

Every number this record states is stated once, on a line of its own shaped `- key: `value``, in the
section that number is a measurement of, and the check recounts each one from the input it measures
rather than reading it as prose: `pending` and `minor` against `.changeset/`, `exports` against
`exportCount` in `release/public-api.json`, `from` against `package.json`, and every classification
row's bump against that declaration's own frontmatter. A section that stops agreeing with the tree
goes red rather than drifting quietly, and a measurement this record declines to state is a finding
rather than a check skipped.

## The decision this records

`@cosyte/hl7` has been publishing on the `0.0.x`-until-first-alpha ladder, and every pending
changeset in this queue was originally filed asking for `patch`, because the repository's own
contributor guidance told every contributor to pick `patch` while that ladder held. A queue
classified that way resolves to `0.0.11` no matter what is in it.

What is in it is not a `0.0.11`. Every declaration classified `minor` below adds behaviour a
consumer can call that did not exist before: five new typed message builders, conformance condition
predicates, coding-system bindings on a value set, a declared profile conformance level, component
rules on a field rule, declared conditional usage with caller-supplied resolutions, a
message-structure registry derived from HL7's published structures instead of hand-transcribed,
typed message overlays that narrow a message to its type, custom-segment field names checked against
the profile that declared them, profile-declared field names on standard segments, an opt-in
validator that checks a message against the published structure for its trigger event, schema
emission for the serialized projection, a widened date-format token vocabulary that can describe a
month name, a 12-hour clock and a single-digit field, and a datetime conversion surface that turns a
parsed value into a plain object or an ISO-8601 string. The aggregate of those `minor` declarations
against `0.0.10` is `0.1.0`, so leaving the ladder is what the queue already says, once each file
says what it actually does.

**Every section below is a function of the tree, not of any earlier certification.** Each
classification row's bump is read from that declaration's own frontmatter and its justification
describes what that file now says; the break candidates are derived from the pending queue and each
is attributed to the declaration that causes it; and the certified export surface is the one a fresh
build produces. No declaration's frontmatter was edited to reach a number: if this queue ever
resolves anywhere other than the target above, that is a finding to report, not a frontmatter to
change.

Nothing in this file bumps a version or publishes anything. The bump is `changeset version`'s, in
the Version PR the release pipeline opens; the publish is `changeset publish`'s after that.

**Publication of `0.1.0` awaits the release frequency policy (S0161); this record certifies that the
queue is ready, not that the release may go out today.**

## Break candidates

A break candidate here is a public export, or a stable warning or finding code, that a pending
changeset **removes, renames or narrows**. Nine were found. They are listed rather than absorbed,
and none of them is being released as a `major`. On a `0.x` line semver carries a breaking change in
the minor position, and `major` would resolve to `1.0.0`, which is a claim that this API is stable at
1.0 and is not the claim this release makes.

Every candidate names the pending declaration that causes it, and the check refuses any declaration
this section names that is not pending in `.changeset/`. That is what makes a carried-over candidate
detectable: a candidate whose cause has already shipped names a file that is no longer in the queue,
and the run says so by name instead of certifying the list. The candidates below are ordered by that
cause, and every pending declaration is accounted for at the end of this section, so silence about
one of them is a finding rather than an absence a reader has to notice.

No pending changeset removes or renames a warning code or a finding code. `WARNING_CODES` stays at
twenty entries; `FINDING_CODES` gains three and renames none. `olive-swans-arrange.md` adds a
separate registry, `STRUCTURE_FINDING_CODES`, rather than extending `FINDING_CODES`, so no consumer
switching over the conformance codes gains an arm from it.

1. **`buildAdt` narrows.** `great-otters-author.md`. For the ten trigger events whose published
   structure requires `MRG` (A40, A41, A42, A43, A44, A45, A47, A49, A50, A51), a call with no
   `priorIdentity` used to return a message carrying a `MISSING_EXPECTED_GROUP` warning and now
   throws a `TypeError` naming the message type and the member that would supply the missing
   segment. Remedy: supply `priorIdentity`, or use `buildMessage` where an incomplete message is
   what is wanted. Every other ADT trigger event is still emitted exactly as before.
2. **`Meta.timestamp` narrows for order-ambiguous slash dates.** `olive-badgers-refuse.md`. A
   slash-separated numeric date whose first two components are both in 1-12 no longer resolves when
   no declared format matched it; `msg.meta.timestamp` comes back `valid: false` with an
   `AMBIGUOUS_DATE_ORDER` report carrying both candidate readings. Remedy: declare the order,
   `parseHL7(raw, { dateFormats: ["MM/DD/YYYY"] })`. A value with one reading, or two readings that
   agree, still resolves.
3. **`MessageStructure.missingGroups` changes what it holds, and warning volume rises.**
   `olive-lions-derive.md`. `missingGroups` used to hold hand-picked group labels such as `"result"`
   and `"patient"` and now holds segment names such as `"OBR"` and `"EVN"`. The field, its type and
   its meaning are unchanged; code matching its values is not, and `missingSegments` and
   `requiredSegments` say the same thing under clearer names. The second half is a behaviour change
   rather than a moved export and is named here for the same reason: more trigger events are
   recognized and more segments are expected per pair, most visibly `EVN` across the ADT family and
   in `MDM` and `DFT^P03`, plus `PV1` in `MDM`, and an `ORU^R01` carrying `OBX` but no `OBR` now
   warns. Remedy: sample your traffic before upgrading if your channel treats a
   `MISSING_EXPECTED_GROUP` warning as a rejection.
4. **`dateFormats` narrows at definition time, and one shape narrows silently at parse time.**
   `olive-melons-teach.md`. `defineProfile()` used to accept any format holding one recognised
   token, so `"MM/DD/YYYY hrs"` and `"YYY/MM"` constructed and then matched nothing forever; every
   character must now be a token or a bracketed literal, and a format that breaks that or the
   `h`/`A`, `SSSS`/`ss` and variable-width-adjacency rules throws a `ProfileDefinitionError` where
   it is written. Remedy: escape a literal letter or digit, `"YYYY-MM-DDTHH:mm:ss"` becoming
   `"YYYY-MM-DD[T]HH:mm:ss"`, which is the change made to the built-in `cerner` profile, so that
   profile's declared format reads differently while matching exactly the same inputs. The quiet
   half is `ParseOptions.dateFormats`, which nothing validates: `M`, `D`, `H`, `h`, `A` and `S` were
   literal letters and are tokens now, so a parse-option format carrying one as text
   (`"MM/DD/YYYY HH:mm Uhr"`) stops matching with no error. Same remedy,
   `"MM/DD/YYYY HH:mm [Uhr]"`. `SUPPORTED_DATE_TOKENS` widening from seven entries to fifteen is
   additive, and `BUILTIN_DATE_FALLBACKS` keeps its membership and order.
5. **`Segment.get` narrows its argument.** `olive-otters-declare.md`. On a segment obtained BY TYPE
   from a message parsed with a statically known profile, `get` accepts only the names that profile
   declares for that segment type, and passing any other literal stops compiling. Nothing narrows at
   run time, and the only calls affected are ones already reading `undefined`, since an undeclared
   name never resolved to a field. Remedy: correct the name, read the segment off
   `msg.allSegments()`, which still takes any `string`, or annotate the profile as the general
   `Profile` interface to give the narrowing up.
6. **`Segment.type` changes what it reports.** `olive-pandas-repeat.md`. It used to carry the wire
   spelling verbatim and now reports the canonical uppercase spelling, which is the field every
   lookup compares. Remedy: read `Segment.raw.name` for the spelling the sender sent.
7. **Strict mode narrows for a lowercase custom-segment claim.** `olive-pandas-repeat.md`. A
   hand-rolled profile keyed with a lowercase `customSegments` name, parsed strict against a
   matching lowercase segment, gains a `SEGMENT_CASE` warning, which strict mode promotes to a
   throw. The parsed result and the profile claim are unchanged; it is the one input strict now
   rejects that it accepted before.
8. **Profile definition narrows on usage and cardinality.** `quiet-pandas-declare.md`. A rule
   pairing `C`, `CE`, `O`, `X`, `B` or a declared conditional with a minimum cardinality above 0, or
   `R` with a minimum of 0, or `X` with a maximum other than 0, defined cleanly before and is now
   `PROFILE_MALFORMED` from `validateAgainstProfile` and a thrown `ProfileDefinitionError` from
   `defineConformanceProfile`. The methodology's own exception is kept: `RE` may carry a minimum
   above 0. Remedy: drop the minimum, or move to `RE` where that exception applies.
9. **`USAGE_CODES` is retyped and `UsageCode` widens.** `tall-comets-declare.md`. `USAGE_CODES` is
   now `readonly UsageCodeRegistryEntry[]`, which is not assignable where a rule usage is expected,
   and `UsageCode` now admits `B` and the declared-conditional template `C(t/f)`, so an exhaustive
   `switch` over it no longer compiles without new arms. Neither type widens to a bare `string`, so
   a typo is still a compile error.

**Additive at run time, breaking an exhaustive `switch` at compile time.** Four changes remove,
rename and narrow nothing and are named here anyway, because the one shape of consumer code that

**A new member on an exported shape.** Two more sit in that category for a different reason.

an optional third parameter, and `olive-turtles-declare.md` puts `level` on every

## Public export surface

- exports: `313`

`release/public-api.json` is the written-down public type surface, derived from a fresh build's
`dist/index.d.ts`: one entry per exported name, with its kind, its printed type and its members. The
count above is the size of the surface this record certifies, and it is `exportCount` in that file.
The readiness check compares the two on every run and refuses an inventory that is absent, is not
JSON, carries no usable count, or states a count its own export list contradicts, rather than
skipping the comparison and reporting a clean queue. `test/scripts/api-surface.test.ts` rebuilds and
re-derives the inventory on every `pnpm test` and fails naming every export that was added, removed
or changed, without rewriting the committed file. It is the baseline a later release is compared
against; it is not itself a claim that the surface is finished.
