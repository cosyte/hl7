"@cosyte/hl7": patch
---

New `readMessages()` and `readSegments()` read HL7 v2 as it arrives: `readMessages(source)` yields each message of a batch, file or feed as soon as it is complete, and `readSegments(source)` yields each segment of one very large message with the warnings about it, so neither ever holds more than the current item. Both take a string, a `Uint8Array` or `Buffer`, a Node `Readable`, a web `ReadableStream`, or any async or plain iterable of string or byte chunks, and read the next chunk only when the next item is asked for, so a slow consumer slows the source rather than filling memory. `readMessages` finds messages as `splitBatch` does (FHS/BHS envelopes and bare concatenated messages alike) and also reads MLLP frames as `@cosyte/mllp` writes them, yielding each frame as soon as its end byte arrives. Each item is the message `parseHL7` gives for exactly its own bytes, warnings and errors included, wherever the chunks were cut, with its `byteOffset`, `byteLength` and `index`; a message that fails to parse is yielded as a failed item carrying its error and its bytes, and reading goes on, while `{ strict: true }` stops at the first failed item and releases the source. `readSegments` gives the same segments, warnings and errors as `parseHL7` for the whole message, with one exception it reports rather than hides: bytes not valid in the character set the message declares throw `UNSUPPORTED_CHARSET`, since `parseHL7`'s fallback of reading the whole message verbatim is not possible once earlier segments have been handed out. In strict mode it throws the first problem in reading order, which for a message with several problems can differ from the one `parseHL7` throws. New types: `Hl7ReadSource`, `ReadMessageItem` and `ReadSegmentItem`. Nothing else changes: `parseHL7`, `splitBatch` and `parseStream` behave exactly as before.
