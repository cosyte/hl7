Fix a defect where a warning or error message could carry clinical text into a log line: on default settings, an unescaped line break inside a narrative field put field content into the message.

`HL7-WARN-MSG-PHI`.

**What leaked, and on what settings.** No options were required: plain `parseHL7(raw)` on lenient defaults. `normalize()` rewrites every `\r\n` and `\n` in the input to `\r` before segment splitting, with no field awareness. HL7 v2 Ch. 2 fixes the segment terminator as `<CR>` and provides `\.br\` (§2.7.6) precisely because a literal line break cannot appear inside a field, but real senders emit raw breaks inside narrative fields (`OBX-5`, notes, embedded documents). When that happens the remainder of the field becomes a forged segment, and `tokenize()` takes the whole line as its segment identifier, because a line with no field separator offers no other candidate. `UNKNOWN_SEGMENT` then interpolated that "identifier" into its message uncapped:

```
Unknown segment "<a line of clinical narrative>": not in HL7 spec and no profile claim.
```

Reproduced with synthetic data carrying name, date of birth and medical record number, all three of which reached `Hl7ParseWarning.message`. Under `{ strict: true }` the same text reached the thrown `Hl7ParseError.message` and therefore `.stack`.

**Why the documented mitigation did not help.** The guidance was to redact `Hl7ParseError.snippet`. On the strict path `snippet` holds the head of the message (usually the MSH header) while `message` held the payload, so a consumer following the advice exactly still logged the data. `message` is also what a logger prints by default and what `stack` embeds, which is what made the inversion consequential.

**What to do if you have a version installed.** Every published version up to and including `0.0.3` is affected. Until you upgrade, treat `Hl7ParseWarning.message` and `Hl7ParseError.message` as potentially containing field content when parsing feeds you do not control, and scrub or drop them at your logging edge rather than only `snippet`. The parsed data itself was never wrong: this is a diagnostic-surface leak, not a mis-parse.

**The fix.** A token taken from input is echoed only when it matches the form the spec defines for it, and is replaced with `<withheld>` otherwise. A shape test rather than a length cap, because truncating still emits the first N characters of a patient name. Segment identifiers are held to exactly three alphanumerics (HL7 v2 Ch. 2 §2.5), with equivalent forms for MSH-9 types and MSH-12 versions. **Charset labels are bounded by registry membership instead, not by spelling**, because Table 0211 is a closed table and `UNKNOWN_CHARSET` fires precisely when a label is absent from it, so at that moment no spec-defined spelling is left to test against and `UNICODE UTF-8` and a patient name are shape-siblings. Conforming tokens render exactly as before, so `PID`, `ZZZ` and every legitimate Z-segment name are unchanged and well-formed input sees no behaviour change. The check sits in the warning factories rather than at the call site, so it also covers the six factories that are currently exported but unreached, and consumers who build warnings themselves.

**What is bounded, stated without overclaiming.** `Hl7ParseError.snippet` is the only field carrying input verbatim and unbounded, so it is the one to redact first. A message cannot carry a field's value, but it can carry a residue of up to three characters when a malformed line happens to look like a segment identifier, so no absolute "never carries field content" claim is made anywhere in this package.

Two related surfaces were bounded in the same pass, and the charset one is the reason the bound is membership rather than shape. `UNKNOWN_CHARSET` and `ENCODING_MISMATCH` interpolate a value read as MSH-18, which on a message carrying no segment terminators is not MSH-18 but the 18th `|`-token of the flattened input, commonly a data field. That path is Buffer-only, and `parseStream` and `splitBatch` re-encode each split message to a Buffer, which is the ordinary MLLP and file ingestion shape. `MISSING_EXPECTED_GROUP` and `MERGE_MISSING_PRIOR_OR_SURVIVOR` interpolate MSH-9.

**Docs corrected in both directions.** `docs-content/troubleshooting.md` asserted that warning messages never echo a field's value, which was an overclaim; it and the equivalent assurances in `normalize.ts` and `warnings.ts` now say the check that makes it true. The `Hl7ParseError` disclosure now states that `snippet` is the field to redact first, and no longer claims that redacting it is sufficient: that was the mitigation this defect proved inadequate. `README.md` described `snippet` as coming from "the offending input" when it is always taken from the start of the message; the wording is corrected rather than the behaviour, because re-pointing the snippet at the deviation's own segment would move more clinical content into the one unredacted field.

**Tests, and the generator gap is the transferable finding.** The property suite could not previously reach the leaking position: every generated marker sat after a `|`, so it was always a field value to the tokenizer, while the only position that leaks is a line's leading token. A green suite over an unreachable case is indistinguishable from a correct one. Ten new tests now cover the real trigger (a field-internal `\n` and `\r\n`) across the lenient and strict arms, the Buffer/MSH-18 path that every string-input generator structurally misses, and the parsed model itself. Each failed on the code it was written against.

**The same lesson applied to this fix's own first draft, which is why it also bounds the model.** Bounding the warning message protected this package's diagnostics and nothing else. `Segment.type` still carried the whole forged line, so a consumer reading the model and building its own report from that "identifier" wrote clinical narrative into it, on lenient defaults, with no options set. A diagnostic-surface fix does not protect a downstream package that reads your model and builds its own diagnostics from it; bounding at the model protects both. `Segment.type`, `Hl7Message.version` and the unrecognized branch of `MessageStructure` now carry bounded identifiers.

**What is deliberately still unbounded, because bounding it would be a mis-parse.** The model separates identifiers from values. `Meta.*` is the documented value view of the MSH header, `Segment.fields` / `Segment.raw` / `Hl7Message.rawSegments` are the raw tokenization that the byte-verbatim round-trip serializes from, and `toString()` / `toJSON()` / `prettyPrint()` are the message itself. Those are content surfaces and are documented as such. Notably `meta.version` keeps MSH-12 exactly as it arrived, and it is what the v2.7 MRG field-scoping reads, so bounding `Hl7Message.version` changes no clinical field selection.

Also corrected while in these files: `docs-content/` gave the warning-code count as 19 (it is 20) and quoted a published npm version that was two releases stale; both now point at the registry instead of restating it.

**One bound deliberately not taken, named rather than left implicit.** On the _recognized_ branch of `MessageStructure`, `triggerEvent` is echoed verbatim, and a definition matching on message code alone (`ACK`) will accept an arbitrary MSH-9.2. That is left unbounded on purpose: no real sender putting narrative in MSH-9.2 is grounded in a de-identified document, and widening the guard there is a separate change rather than a silent extension of this one. An earlier comment in that file claimed the branch returned registry values and could not carry input, which was wrong; the claim is corrected rather than the guard grown.
